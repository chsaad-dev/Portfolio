What I Learned Building My First Production Android App: SpendWise Expense Tracker

📅 Published: November 26, 2026 · ⚡ Updated: November 26, 2026 · ⏱️ 7 min read · 👨‍💻 Muhammad Saad

There is a huge gap between an Android app that runs cleanly on your Pixel emulator and a production app that real people install from the Google Play Store. When I started building SpendWise—an offline-first personal finance and budget-envelope app—I thought the hardest part would be writing Room queries or drawing spending charts.

I was wrong. The real engineering lessons showed up in the final 20% of polish: the subtle cold-launch flicker, SQLite file-locking bugs during database backups, dropped frames when switching tabs on mid-range phones, and the discipline required to ship a signed, R8-minified release build to Google Play. Here is what building and shipping my first production Android app taught me.

1. "Works on My Emulator" Hides Real-World Frame Drops

In the early versions of SpendWise, navigating between the five main screens—Home, History, Categories, Goals, and Settings—used standard replace() transactions. On a fast desktop emulator with 16 GB of RAM, it felt instant. On a real budget Android device with real transaction data, re-inflating views and re-attaching chart observers on every tab tap caused noticeable micro-stutters.

The fix was switching to a show-and-hide fragment caching strategy. Each of the five tabs is inflated once, kept in memory, and toggled with a subtle 110ms fade-in and 90ms fade-out—with zero scale or translation jitter. Tab switching immediately became predictable and buttery smooth, even on lower-end hardware.

2. Cold-Launch Empty-State Flashes Ruin First Impressions

Even with fast local Room queries, reading SQLite from disk is asynchronous. During the first few milliseconds of a cold launch, before Room emitted its first Flow value, SpendWise briefly rendered a "No transactions yet" empty state and a blank chart—only to snap to the user's real balance a frame later.

That tiny 100ms flash makes an app feel amateurish. I learned to model UI loading state explicitly: keep empty-state views hidden by default until the first Room database emission actually completes. Only when the database confirms zero rows should the empty state appear.

3. SQLite WAL Checkpointing Is Non-Negotiable for Backups

Because SpendWise is 100% offline-first—no user financial data ever leaves the phone—giving users a reliable local database backup and restore feature was critical. My first naive attempt simply copied the primary .db file.

That is a dangerous trap in Android. Room enables Write-Ahead Logging (WAL) by default, meaning recent transactions often live inside -wal and -shm sidecar files rather than the main database file. Copying only the .db file without flushing the WAL produces incomplete or corrupted backups. 

// Always checkpoint Room's WAL before copying the SQLite file for backup
@Dao
interface MaintenanceDao {
    @RawQuery
    suspend fun checkpoint(supportSQLiteQuery: SupportSQLiteQuery): Int
}

suspend fun flushWalBeforeBackup(maintenanceDao: MaintenanceDao) {
    maintenanceDao.checkpoint(SimpleSQLiteQuery("PRAGMA wal_checkpoint(FULL)"))
}

Running PRAGMA wal_checkpoint(FULL) (and closing/re-opening the Room instance cleanly on restore) guaranteed that every exported backup contains 100% of committed transactions.

4. Edge-to-Edge, Gesture Bars, and Real Device Polish

Modern Android spans dozens of OEM skins, notch shapes, and Android 12–16 gesture navigation bars. Going edge-to-edge in SpendWise—especially with a floating frosted-glass bottom bar using RenderEffect blur on Android 12+ and a full-screen pinch-to-zoom receipt viewer—taught me to respect WindowInsets everywhere.

Every floating button, modal bottom sheet, and scroll container needs proper system bar padding so the navigation pill never collides with the gesture handle or clips behind the status bar. Similarly, theme switching (System / Light / Dark) should apply immediately via AppCompatDelegate without jarring Activity restarts.

5. Shipping to Google Play Teaches Discipline

Publishing SpendWise on Google Play forced a level of rigor that debug builds never demand:

  • Release Minification (R8 / ProGuard): Testing the actual signed .aab release bundle—not just debug APKs—to ensure Room entities, PDF exporters, and WorkManager reminder workers survive code shrinking and obfuscation.
  • Privacy-First by Design: Keeping financial records strictly on-device made Google Play's Data Safety declaration transparent and trustworthy—zero third-party tracking of user expenses.
  • Production Observability: Pairing offline reliability with Firebase Crashlytics and Remote Config so unexpected OEM-specific crashes can be caught and feature flags toggled without waiting for another app review cycle.

Conclusion: Finished Means Shipped

Building SpendWise taught me that production quality is rarely about one massive architectural breakthrough—it is the sum of dozens of small, deliberate decisions: eliminating a 100ms empty-state flash, checkpointing SQLite WAL files before backup, keeping tab transitions lag-free, and testing signed release bundles on real hardware.

You can try SpendWise today on the Google Play Store or inspect the full Kotlin codebase on GitHub.
